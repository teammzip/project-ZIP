# 최신 요구사항 반영 및 검증 범위 (2026-11-02)

검토 기준은 HEAD `7bb1c90`의 API.md, community/reports.ts, life/types.ts·store.ts, onboarding/store.ts·SurveyPage.tsx입니다. 스키마는 44개 테이블·356개 컬럼·기본키/UNIQUE 71개·외래키 62개·CHECK 14개·VIEW 2개입니다. 이 문서는 DB와 미래 백엔드의 저장 계약을 정리하며 API 구현 완료를 뜻하지 않습니다.

## 1. 신고

- UNIQUE `uk_reports_reporter_target(reporter_id,target_type,target_id)`로 같은 회원의 같은 대상 재신고를 막습니다. 사유가 다르거나 처리 상태가 DISMISSED/HIDDEN으로 바뀌어도 재신고할 수 없습니다. 다른 회원의 같은 대상 신고는 허용합니다.
- COMMENT의 target_id는 서버의 comments.id입니다. 현재 브라우저의 댓글 순번을 그대로 넣으면 댓글 삭제/정렬 후 다른 댓글을 가리킬 수 있습니다. 서버 연결 시 안정적인 ID로 변환해야 합니다.
- 서버는 reporter_id를 로그인 세션에서 결정하고 실제 대상 존재·본인 대상 여부·제재 상태를 검사합니다. 중복 INSERT의 1062가 이 키에서 발생하면 API의 409와 사용자용 message로 변환합니다. 다른 UNIQUE/FK 오류를 무조건 중복 신고라고 응답하지 않습니다.
- target_author_snapshot과 target_text_snapshot은 신고 당시 작성자 표시명과 글 제목/댓글 내용입니다. 클라이언트가 보낸 값을 신뢰하지 않고 실제 대상에서 복사합니다. 기존 신고는 NULL을 허용하며 삭제된 대상 정보를 임의 복원하지 않습니다.
- 신고 대상이 삭제된 후 관리자 조회는 실제 대상이 없거나 deleted 상태인지 판정하고 스냅샷을 대체 표시합니다. 신고 처리 API는 같은 target_type/target_id의 처리 대기 행을 함께 갱신하고 관리자 ID·처리 시각을 기록합니다. 원본 글/댓글 변경과 신고 상태 변경은 트랜잭션으로 묶습니다.
- DB가 신고 대상 존재·종류·작성자·관리자 역할을 자동 검증하거나 글 삭제 시 신고 상태를 자동 변경하는 것은 아닙니다. `staff` 댓글 표시도 users.role을 조회해 응답하며 별도 boolean을 중복 저장하지 않습니다.

## 2. 위치 정보의 의미

| 프론트 값 | DB | 의미 |
|---|---|---|
| HousingSurvey.addressPoint.lat/lon | housing_surveys.address_lat/address_lon | 설문 주소 검색 당시 행정구역 중심점 스냅샷 |
| LifeSettings.regionLocation.region | user_settings.region_name | 현재 동네 표시명 |
| regionLocation.source | user_settings.region_source | survey/verified/manual → SURVEY/VERIFIED/MANUAL |
| regionLocation.point.lat/lon | user_settings.region_lat/region_lon | 출처에 따라 행정구역 중심 또는 인증 위치 |
| regionLocation.userId | user_settings.user_id | 인증된 소유자, 요청 본문 ID를 신뢰하지 않음 |
| users.home_lat/home_lon | 기존 컬럼 유지 | 집 주소 기반 좌표, 인증 GPS와 혼용하지 않음 |
| RegionVerify.at | users.region_verified_at | 동네 인증 시각, 현재 동네를 기준으로 유효성 검사 |

source=NULL이면 위치 묶음 전체가 미설정이며 regionLocation을 생략합니다. source가 있으면 빈칸이 아닌 region_name을 요구합니다. point는 생략 가능하지만 있으면 위도·경도 모두 필요하며 범위는 위도 -90~90, 경도 -180~180입니다. 0도는 유효합니다. 행정구역 정규화/region_id 매핑은 서버가 처리하고 표시명만 같다고 동일 지역으로 단정하지 않습니다.

설문 주소 선택 시 SURVEY 출처와 중심점을 저장하고 같은 주소여도 재설문에 따른 인증 초기화 정책을 적용합니다. 수동 주소 변경은 좌표를 비우거나 재계산하고 인증을 초기화합니다. 인증 시에는 서버 검증 후 VERIFIED로 저장하며 과거 설문 스냅샷과 집 좌표를 덮어쓰지 않습니다. users, user_settings, housing_surveys 변경을 하나의 트랜잭션에서 수행합니다. DB CHECK는 다른 테이블의 인증 시각까지 검사하지 않으므로 이 처리는 API 책임입니다.

## 3. 추가 DB 제약

- 집 좌표와 설문 좌표: 둘 다 NULL이거나 둘 다 유효한 범위.
- 지도 장소: 유효한 위경도 범위.
- 리뷰 별점: 1~5.
- 배출 요일: 0~6.
- home_memo_ids: NULL 또는 길이 최대 3의 JSON 배열.
- map_categories/map_keywords: NULL 또는 JSON 배열.

JSON 배열 원소의 문자열 타입·중복·실제 메모 소유자·분류 존재 여부와 items의 text/done 스키마는 API에서 검사합니다. DB가 JSON 내부 ID를 외래키로 검사하지 않습니다. 메모 삭제 후 설정 정리와 리뷰 집계 카운터 갱신도 자동 수행되지 않습니다.

## 4. 개인정보·기존 데이터

기존 동의 문구를 덮어쓰지 않았습니다. 실제 수집 전 설문 좌표·위치 출처·신고 스냅샷의 목적·보관기간·접근권한을 정책에 반영해야 합니다. 위치 이력을 쌓는 테이블은 만들지 않았으며 현재값과 설문 응답 스냅샷만 저장합니다. 최소한의 좌표 정밀도와 필요한 보관기간을 정합니다.

신고자가 탈퇴하면 그 회원의 신고는 기존 FK에 따라 삭제됩니다. 대상 작성자가 탈퇴해도 타인의 신고 자체는 남을 수 있습니다. 작성자 표시명/본문 스냅샷도 개인정보를 포함할 수 있으므로, 회원 삭제 전에 관련 대상을 찾고 스냅샷 마스킹/삭제 또는 별도 정당한 보관 절차를 수행해야 합니다. 이 정책을 구현하기 전 탈퇴 후 개인정보 삭제 완료로 안내해서는 안 됩니다. 새 UNIQUE를 적용하기 위해 기존 중복 신고를 자동 삭제하지 않습니다.
