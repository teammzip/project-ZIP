# 백엔드 착수 전 설계 점검 — 2026-11-07

대상: HEAD `1a41a75` + 현재 DB 작업 트리. React 파일과 실행 중인 사용자 DB는 변경하지 않았습니다.

판정: 현재 기능을 구현할 저장 구조는 갖추었습니다. 아래 서비스 규칙을 인수 기준에 포함해 백엔드 구현을 시작할 수 있습니다. 현재 스키마를 운영 완료 또는 모든 예외에 안전하다고 판정한 것은 아닙니다.

## 우선 확정·구현할 사항

### 1. 지출 합계의 의미와 사용자 분류 (높음)

`schema.sql`의 v_monthly_spend_breakdown은 모든 고정 지출을 '공과금' 한 줄로 합칩니다. paid_at 필터도 없으므로 미납 청구액을 포함합니다. 사용자 bill 태그별 차트나 실제 납부 총액에 그대로 사용하면 결과의 의미가 달라집니다. 이는 현재 VIEW 정의에서 확인한 동작이며 이번 정적 검사나 이전 구조 감사가 잡는 실패 조건은 아닙니다.

백엔드에서는 예상 고정 지출, 납부 완료, 기타 실제 지출을 구분해 응답합니다. 카테고리별 고정 지출은 bill_items.tag로 집계하되, 월별 bill_payments.amount를 금액의 기준으로 사용합니다. 납부 완료만 계산할 때는 paid_at IS NOT NULL을 적용합니다. VIEW의 기존 의미를 바꾸려면 의존하는 가계부·AI 조회와 테스트도 함께 변경해야 하므로 이번 리뷰에서 임의로 바꾸지 않았습니다.

월별 청구 행 생성 시점과 재실행 정책도 필요합니다. 사용하지 않던 과거 월의 청구액을 현재 default_amount로 임의 복원하지 않습니다. 월 중 금액 수정은 현재/미래 어느 월에 적용할지 API 계약에 명시합니다. 항목 제거는 기본적으로 is_active=0으로 처리해 과거 납부 행을 보존하고, 과거 기록까지 지우는 별도 동작과 구분합니다. FK CASCADE가 있으므로 단순 DELETE는 과거 기록도 지웁니다.

### 2. 회원 소유권과 참조 대상 일치 (높음)

events/user_id와 category_id는 각각 FK지만 같은 회원인지는 검사하지 않습니다. event_presets, 첨부 파일, 프로필 사진에도 동일한 서비스 검증이 필요합니다. comments.parent_id는 실제 댓글 존재만 확인하며 같은 게시글인지 확인하지 않습니다.

인증된 회원 ID + 대상 ID로 조회/수정하고, 카테고리·파일 참조의 소유자를 같은 트랜잭션에서 검사합니다. 다른 글의 부모 댓글, 순환 부모 연결은 거부합니다. 소유권을 DB에서도 보장하려면 복합 FK 등 별도 설계가 필요하지만, 현재의 SET NULL/CASCADE 정책과 함께 검토해야 합니다. 기존 FK만으로 권한 검사가 된다고 간주하지 않습니다.

### 3. 인증 식별자 비교와 세션 무효화 (높음)

provider_user_id는 명시적 collation 없이 DB 기본 utf8mb4_0900_ai_ci를 따릅니다. 공급자 식별자는 불투명한 문자열로 취급하고 비교 규칙을 공급자 계약에 맞춰야 합니다. 대소문자를 구분하는 식별자가 들어올 경우 현재 UNIQUE/조회가 같은 값으로 취급할 수 있으므로, 소셜 로그인 구현 전에 이 컬럼을 대소문자 구분 비교로 변경할지 확정하고 기존 충돌 검사를 포함한 마이그레이션을 작성합니다. 이메일만으로 기존 회원에 소셜 계정을 자동 연결하지 않습니다.

auth_sessions에는 refresh 해시/만료/해제 시각이 있지만, API 문서에는 refresh 경로가 명확히 정해져 있지 않습니다. 로그인 유지 시 재발급 방식을 정하고, access token의 세션 식별자를 auth_sessions.id와 연결해 로그아웃·비밀번호 변경·정지 시 무효화 정책을 구현합니다. 서명/만료만 검사하는 access token은 세션 revoked_at만 바꿔도 즉시 차단된다는 보장이 없습니다.

password_hash VARCHAR(100)은 사용하는 해시 인코딩 길이를 확인해야 합니다. bcrypt를 고정 사용하면 수용 가능하지만 다른 알고리즘/파라미터로 전환할 계획이면 VARCHAR(255) 등으로 확장하고 이관 테스트를 추가합니다. 이번 검토에서 특정 알고리즘 사용을 가정해 SQL을 바꾸지는 않았습니다.

### 4. 개인 카테고리와 공용 분류 사전 (중간)

현재 JSON 설정 + ledger_categories 사전 방식으로 추가/정렬 기능을 지원할 수 있습니다. 다만 개인 색/순서는 JSON에서, 기록 참조는 사전에서 읽어야 합니다. JSON 전체를 덮어쓰면 동시에 수정한 다른 scope가 사라질 수 있어 트랜잭션 행 잠금 또는 버전 충돌 검사가 필요합니다.

프론트는 대소문자를 무시해 중복을 검사하지만 DB 사전은 기본 accent-insensitive collation을 사용합니다. 서로 다른 회원이 추가한 이름을 사전 키로 합칠 때 비교 규칙이 달라질 수 있습니다. 이름 정규화·중복 판정을 서버와 DB에서 일치시키고, 향후 이름 변경/삭제·복잡한 검색이 필요해지면 회원별 정규화 테이블로 옮기는 것이 좋습니다. 현재 기능에는 JSON 저장을 유지할 수 있습니다. JSON 내부 구조·최대 항목 수는 API에서 제한합니다.

### 5. 날짜·금액·계층의 API 제약 (중간)

rent_day 범위, 연월 YYYY-MM, 일정 시간 00:00~23:59, boolean 0/1, 완료 여부/done_at 일치 등은 모든 컬럼에서 DB CHECK로 보장되지 않습니다. MySQL 타입에 들어갈 수 있다는 사실과 사용자 입력으로 유효하다는 사실을 구분합니다. API 입력 DTO 검증과 실패 시 DB 변경 없음 테스트가 필요합니다.

BIGINT ID는 문자열로 전송합니다. 금액은 원 단위 정수이며 rent_amount만 만원 단위입니다. JS 안전 정수 범위를 넘는 금액을 그대로 number로 보내지 않도록 API 금액 상한을 정하고, SQL 집계 결과의 범위도 검사합니다. DATETIME의 저장 기준은 UTC로 통일하고 월 경계·납부일 계산은 Asia/Seoul 기준으로 수행하는 방식을 권장합니다. 기존 데이터의 시간 기준을 확인하지 않고 UTC로 재해석하지 않습니다.

regions의 (parent_id,name) UNIQUE만으로 parent_id=NULL인 최상위 지역의 중복은 막히지 않습니다. 지역 마스터 생성 절차에서 루트 중복·순환 계층·자기 자신을 이웃으로 추가하는 입력을 거부합니다. 회원 API가 공용 지역 마스터를 직접 수정하지 않도록 합니다.

### 6. 삭제·외부 저장소·운영 절차 (구현/배포 기준)

회원 삭제 전 관련 파일의 저장소 키와 신고 스냅샷 정리 대상을 확보합니다. DB CASCADE는 실제 파일을 지우지 않습니다. 파일 정리 실패 재시도, 차단 해시 만료/키 버전, 미연결 휴대전화 인증 기록 정리도 구현 대상입니다. 약관 기존 버전은 덮어쓰지 않고, 현재 예시 문구와 실제 수집·보존 정책의 일치 여부는 별도로 검토해야 합니다.

런타임 DB 계정과 DDL 계정을 분리합니다. 공용 VIEW도 반드시 회원 필터를 적용합니다. 목록 인덱스는 실제 API 쿼리와 EXPLAIN으로 검증합니다. 전체 데이터 조회·관리자 상태별 조회·날짜 검색 성능은 소규모 가상 데이터 테스트로 보장되지 않습니다. 백업 복원·배포 실패 후 복구는 별도의 운영 검증입니다.
