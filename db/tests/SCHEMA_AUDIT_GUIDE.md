# 전체 스키마 구조 대조

## 실행

앞선 가상 데이터 테스트를 정리한 뒤 zip_test의 새 연결에서 15_schema_audit.sql을 열어 전체 실행합니다. 테이블·사용자 데이터는 변경하지 않습니다. 세션 변수와 결과 표시용 group_concat_max_len만 잠시 설정하고 마지막에 이전 설정으로 돌립니다. 트랜잭션을 시작하거나 DDL을 실행하지 않으므로 ROLLBACK은 필요하지 않습니다.

최신 db/schema.sql(2026-11-07 변경 반영)의 구조 스냅샷을 기대값으로 사용합니다. schema_expected.json은 동일한 기대값을 읽기 쉽게 보관한 메타데이터로 실제 회원 정보가 아닙니다. SQL은 JSON을 자체 포함하므로 JSON 파일을 별도로 가져올 필요는 없습니다. 스키마가 바뀌면 두 파일의 기대값도 함께 갱신해야 합니다.

## 예상 결과

| ID | 검증 내용 | checked_count |
|---|---|---:|
| M01 | 전체 기본 테이블 존재 | 44 |
| M02 | 컬럼 타입·NULL·AUTO_INCREMENT·생성컬럼 여부·명시된 문자셋/정렬 규칙 | 358 |
| M03 | PRIMARY/UNIQUE의 이름과 컬럼 순서 | 71 |
| M04 | FK의 이름·출발 컬럼·대상 DB/테이블/컬럼·삭제 규칙 | 62 |
| M05 | CHECK 존재 및 ENFORCED=YES | 15 |
| M06 | VIEW 존재 및 출력 컬럼 순서 | 2 |
| M07 | 테이블 저장 엔진 InnoDB | 44 |

각 결과가 result=PASS, failed_count=0, failed_items=NULL이어야 합니다. NULL은 실패 항목이 없다는 뜻입니다. 검증 대상 행이 0이면 통과로 판단하지 말고 checked_count를 표와 비교합니다.

뒤의 추가 객체 목록과 추가 컬럼 목록은 기본적으로 빈 결과가 예상됩니다. 이전 데이터 이전용 todos_legacy_20261031이 추가 객체로 나올 수 있으며 이 경우 보관용인지 확인한 뒤 예외로 기록합니다. 추가 객체를 자동 삭제하지 않습니다. is_anniv/is_yearly 같은 기념일 중복 컬럼이 나온다면 기존 마이그레이션 충돌 여부를 확인합니다.

M02는 MySQL 버전별 정수 표시 폭 차이를 무시합니다. 예를 들어 bigint(20) unsigned와 bigint unsigned는 같은 저장 범위로 취급하지만 int와 bigint는 다르게 판단합니다. 이 방식은 크기 부족 같은 오류를 찾아내기 위한 것입니다.

## 실패할 때

금액 컬럼 5개만 M02에 남은 부분 적용 사례는 [16_align_money_types.sql](16_align_money_types.sql)을 사용합니다. 전체 실행하지 말고 R00 정리 → R01 실제 타입 조회 → 필요한 R02 ALTER 선택 → R03 확인 → 15번 재실행 순서입니다. 앞선 가상 데이터 테스트와 달리 실제 DDL이며 ROLLBACK으로 취소할 수 없습니다. 테스트 DB 밖에서는 사용하지 않습니다.

failed_items에 나온 테이블·컬럼·제약조건을 복사하고 해당 테이블의 SHOW CREATE TABLE 결과를 확인합니다. 파일을 재실행한다고 누락 타입이 자동 수정되는 것은 아닙니다. 원인 확인 없이 전체 마이그레이션을 재실행하거나 테이블을 삭제하지 않습니다.

```sql
USE zip_test;
SHOW CREATE TABLE incomes;
```

SQL_MODE에 NO_BACKSLASH_ESCAPES를 지정한 특수 환경에서는 JSON 문자열/정규식 해석이 달라질 수 있습니다. 오류가 있다면 MySQL 버전과 SELECT @@sql_mode 결과를 함께 확인합니다. 서버 설정을 임의로 해제할 필요는 없습니다. MySQL 실행 오류는 구조 검증 FAIL과 별도로 기록합니다.

## 이 검사 이후 남는 작업

이번 검사는 구조의 주요 속성을 비교합니다. DEFAULT·ON UPDATE·비고/표시 순서, 일반 조회 인덱스, 명시되지 않은 기본 문자셋, FK ON UPDATE, CHECK/생성컬럼/VIEW의 수식 자체가 동일한지까지 자동 증명하지 않습니다. M05가 통과해도 CHECK의 실제 거부 동작은 별도 INSERT 테스트로 확인해야 합니다. M06도 집계 수식이 맞는지는 앞선 데이터 테스트와 추가 검증으로 확인합니다.

다음 보완 항목이 남아 있습니다.

- 과거 P/N·A/B 중 정확한 개별 결과가 아직 없는 항목: RESULTS.md의 미확인 상태 확인.
- users.phone, phone_verifications.verified_token_hash 및 일부 회원별 PK는 17번 보완 테스트에서 검사합니다.
- 주거 설문·대출 스냅샷의 대표 추가 경계값은 17번에서 검사합니다. 모든 입력 조합을 검증한 것은 아닙니다.
- 62개 FK 전체에 대한 부재 참조·삭제 동작 조합은 현재 일부만 실행했으므로 미실행 조합 보완.
- 기존 35개부터의 가상 이전 보존 검증은 18~20번으로 수행했습니다. 운영 백업 복원은 별도 검증입니다. 현재 최신 zip_test에 초기 마이그레이션을 실행하지 않습니다.
- API 소유권·관리자 권한·동시성·인증 만료·자동 작업은 백엔드 구현 이후 확인.

기능별 대표 데이터 테스트와 이번 구조 대조가 통과하더라도 '모든 경우의 테스트 완료' 또는 '운영 검증 완료'로 표기하지 않습니다.
