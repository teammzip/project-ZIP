2. 왜 이걸 골랐나 (핵심만)
====================================================================
[Java 21]
  - Spring Boot 3 는 Java 17 이상이 필요하고, 21 은 오래 지원되는 LTS 라 안전하다.
  - 팀원이 자바 문법을 배우면서 쓰기에도 자료가 가장 많다.

[Gradle]
  - build.gradle 한 파일에 의존성(라이브러리)을 적는다. Maven(pom.xml)보다 짧다.
  - 어느 쪽이든 동작은 같다. 팀원이 Maven 에 익숙하면 Maven 도 괜찮다.

[Spring Data JPA]
  - events, bills, posts 같은 표를 클래스(Entity)로 만들면 저장/조회가 쉬워진다.
  - 단점: 연관 관계가 많으면 느려질 수 있다(N+1 문제). 목록 조회는 필요한 칸만 가져오게 짠다.
  - 통계/관리자 검색은 QueryDSL 이나 직접 쓴 쿼리로 보완한다.

[Spring Security + JWT]
  - 프론트가 이미 "Authorization: Bearer <토큰>" 을 보내고, 401 이면 자동 로그아웃한다.
  - 비밀번호는 BCrypt 로 해시해 저장한다 (Spring Security 기본 제공).
  - 로그인 유지(remember)는 토큰 만료 시간을 길게/짧게 해서 맞춘다.
  - 토큰 재발급(refresh)은 httpOnly 쿠키 방식을 추천 (API.md 1번).

[OAuth2 Client]
  - 카카오/네이버/구글 로그인을 설정만으로 붙일 수 있고, 프론트가 이동하는 주소가
    기본 경로와 같아서 맞추기 쉽다. 끝나면 /oauth/callback?token=... 으로 돌려보낸다.

[Flyway]
  - 표를 바꿀 때마다 V1__, V2__ 파일로 순서대로 기록해서 모두의 DB 를 같게 맞춘다.
  - 6번 주의 참고.

[Testcontainers]
  - 테스트할 때 진짜 MySQL 8 컨테이너를 잠깐 띄운다. 스키마의 CHECK, JSON 칸 등을
    그대로 검증할 수 있다. (Docker 가 설치되어 있어야 함)

[springdoc(Swagger)]
  - 코드에서 API 문서 화면을 자동 생성한다. frontend/API.md 와 실제 서버가 어긋나는지
    확인하는 용도로 좋다.

4. 프로젝트 구조 추천 (프론트 features 와 이름을 맞추면 찾기 쉬움)
====================================================================
  com.zip
  ├─ ZipApplication.java
  ├─ common/            공통 (오류 응답 { message }, JWT, 보안 설정, CORS, 시간대)
  ├─ auth/              로그인, 회원가입, 휴대폰 인증, 소셜 로그인
  ├─ user/              내 정보, 설정, 동네(region), 프로필
  ├─ event/             일정, 카테고리, 항목 버튼, 쓰레기 배출
  ├─ money/             월세, 고정지출(bill), 가계부(수입/지출), 통계
  ├─ notification/      알림
  ├─ community/         글, 댓글, 좋아요, 첨부(파일), 신고
  ├─ memo/
  ├─ support/           고객센터
  ├─ ai/                AI 상담
  ├─ place/             지도 장소, 즐겨찾기
  ├─ admin/             관리자, 이용 정지
  └─ external/          외부 API 호출 (주소, 날씨, SMS, AI)

  각 폴더 안은 Controller(주소) -> Service(로직) -> Repository(DB) -> Entity(표) + dto(요청/응답)
  로 나눈다. 프론트 폴더(features/auth, features/life ...)와 같은 이름으로 맞추면
  "이 API 는 화면 어디서 쓰지?"를 바로 찾을 수 있다.


5. 프론트와 맞춰야 해서 꼭 챙길 설정 (놓치기 쉬움)
====================================================================
  1) id 를 문자열로 내려주기
     DB 의 BIGINT id 를 JSON 에서 "12" 처럼 문자열로 줘야 한다 (JS 숫자 범위 문제).
     Jackson 에서 Long -> String 으로 직렬화하도록 전체 설정한다.
  2) 오류 응답 통일
     실패는 { "message": "이미 가입된 이메일이에요." } 형태, 이 문장이 화면에 그대로 보인다.
     @RestControllerAdvice 로 한 곳에서 처리한다.
  3) 시간대 Asia/Seoul
     서버, JDBC, Jackson 모두 한국 시간으로 맞춘다. 날짜 'YYYY-MM-DD', 시각 'HH:MM',
     일시는 ISO ("2026-10-24T09:00:00+09:00") 로 준다.
  4) JSON 키는 camelCase (rentDay), DB 칸은 snake_case (rent_day)
     Hibernate 기본 네이밍 전략이 변환해 준다.
  5) 401 / 403 / 404 규칙
     토큰 없음/만료 401, 권한 없음 403, 남의 데이터는 404 (내 것만 조회/수정).
  6) CORS / 개발 프록시
     프론트 localhost:3000 이 /api 요청을 백엔드 localhost:8080 으로 넘긴다 (vite.config.ts).
  7) 소셜 로그인 후 돌려보내기
     성공하면 프론트의 /oauth/callback?token=<accessToken> 으로 redirect.
  8) 목록 응답 { items, hasNext } 와 ?page=0&size=20
  9) 입력 검사 규칙을 프론트(schema.ts)와 똑같이
     아이디 6~16자 영소문자+숫자, 비번 8~16자 영문+숫자+특수, 닉네임 2~12자 등.


6. 꼭 상의할 것: Flyway 와 기존 마이그레이션 (DB 담당 문원과)
====================================================================
  - 지금 db/ 에는 schema.sql 과 날짜 이름의 마이그레이션(20261031_*.sql 등)이 있다.
    Flyway 는 V1__이름.sql 처럼 정해진 형식의 이름을 요구하므로 그대로는 못 쓴다.
  - 방법 A) schema.sql 현재 상태를 V1__init.sql 로 만들고, 앞으로의 변경만 V2__ 부터 Flyway 로 관리
  - 방법 B) Flyway 를 쓰지 않고 지금처럼 db/ 폴더 SQL 을 사람이 순서대로 실행
  - 추천: 팀이 같은 DB 를 쓰는 환경이면 A. 다만 DB 담당과 합의 후 한 쪽으로만 관리할 것
    (두 곳에서 따로 표를 바꾸면 서로 어긋난다).
  - JPA 의 ddl-auto 는 update/create 를 쓰지 말고 validate 또는 none 으로 둔다.
    (표는 schema.sql 이 기준이고, JPA 가 마음대로 표를 바꾸면 안 된다)
  - 알려진 이슈: 기념일 칸 정식 이름은 is_anniversary / repeat_yearly (예전 이름 사용 금지)

7-1. AI 업체 선택 기준과 비교 테스트 방법
====================================================================
후보: Claude(Anthropic), Gemini(Google), Grok(xAI), GPT(OpenAI) 등
주의: 요금, 무료 한도, 모델 이름은 자주 바뀐다. 이 문서에는 적지 않았다.
      키를 발급받는 시점에 각 업체 사이트에서 직접 확인할 것.
결론 먼저: 한 업체로 확정하지 말고, 바꿔 끼울 수 있게 만든 뒤 같은 질문으로 비교해서 고른다.

[A] 선택 기준 (이 앱 기준)
  기준              왜 중요한가                                     확인할 것
  ----------------  ----------------------------------------------  ---------------------------------------
  한국어 품질       자취 상담, 집주인에게 보낼 정중한 문자 초안     직접 써 보고 판단 (아래 C 테스트)
  사진 입력         분리배출, 냉장고 요리, 청소·곰팡이, 집주인 문자는 사진을 받음   쓰려는 모델이 이미지 입력을 지원하는지
  비용·무료 한도    팀 프로젝트라 예산이 거의 없음                  지금 요금, 무료 크레딧/무료 티어 여부와 한도
  연동 편의         Spring 서버에서 호출해야 함                     REST 호출 형식이 단순한지, 자바에서 쓸 SDK나 예제가 있는지
  정해진 형식 응답  지출 요약 카드, 지도/링크 카드를 만들어야 함     JSON 같은 구조화된 출력을 안정적으로 주는지
  응답 속도         채팅 화면이라 오래 걸리면 답답함                 첫 글자가 나오기까지 시간, 스트리밍 지원 여부
  요청 제한         사용자가 몰리면 막힐 수 있음                     분당/일일 요청 수 제한
  개인정보          월세, 지출 같은 정보가 외부로 나감               입력 데이터를 학습에 쓰는지, 보관 기간, 삭제 요청 가능 여부
  안정성            서비스가 중간에 끊기면 AI 화면이 멈춤           장애 시 대체 업체로 넘어갈 수 있는지

[B] 구조: 업체를 바꿔 끼울 수 있게 만들기 (Spring)
  - ai 패키지에 "AI 호출 인터페이스" 하나를 만든다.
      예) interface AiClient { AiReply ask(AiRequest request); }
  - 업체마다 구현 클래스를 따로 둔다 (ClaudeAiClient, GeminiAiClient, GrokAiClient ...).
  - 어떤 업체를 쓸지는 설정값(application.yml 또는 .env)으로 고른다.
  - 컨트롤러와 서비스는 AiClient 만 알고, 특정 업체를 모른다.
      -> 업체를 바꿔도 프론트 API(/api/ai/...)와 화면은 그대로.
  - 공통으로 처리할 것(한 곳에서):
      * 분야(topic)별 안내 문구(시스템 프롬프트)
      * 하루 사용량 제한 (ai_usage_daily)
      * 사진 크기/형식 검사
      * 오류가 나면 "잠시 후 다시 시도해 주세요" 같은 일정한 메시지
      * 질문/답변 기록 저장 (ai_conversations, ai_messages)
  - 키는 서버 .env 에만 둔다 (프론트에 넣지 않음, 깃에 올리지 않음).

[C] 비교 테스트 방법 (직접 해보는 것이 가장 정확하다)
  1) 준비: 후보 업체 2~3곳의 키를 받아 같은 입력으로 호출하는 간단한 테스트 코드를 만든다.
  2) 질문 세트: 앱의 AI 분야 10개에서 하나씩 뽑아 총 10개 질문을 정한다.
       분야            테스트 질문 예시
       qna 자유 질문   "자취 처음인데 제일 먼저 사야 하는 게 뭐예요?"
       guide 사용 방법 "월세 납부 체크는 어디서 해요?"  (앱 기능 안내가 맞는지)
       nearby 근처 탐색 "서울 마포구 근처에서 밤에 갈 수 있는 약국 알려줘"
       trash 분리배출  (사진) 치킨 박스 / 깨진 유리컵 사진 + "이건 어떻게 버려요?"
       cook 냉장고 요리 (사진) 냉장고 재료 사진 + "이걸로 한 끼 만들 수 있어요?"
       clean 청소·곰팡이 (사진) 욕실 곰팡이 사진 + "어떻게 지워요?"
       contract 계약·보증금 "퇴거할 때 보증금 돌려받으려면 뭘 확인해야 해요?"
       landlord 집주인 문자 (사진) 누수 사진 + "집주인에게 정중하게 수리 요청 문자 써줘"
       bill 공과금·생활비 "전기요금 줄이는 방법 알려줘"
       summary 지출 요약 월세, 공과금, 식비 숫자를 넣고 "이번 달 지출 요약해줘"
     (사진이 필요한 4개는 직접 찍거나 구한 사진을 같은 것으로 모든 업체에 보낸다)
  3) 같은 조건으로 호출: 같은 질문, 같은 안내 문구, 같은 사진으로 업체마다 한 번씩.
  4) 점수표로 기록 (각 항목 1~5점):
       항목              업체 A    업체 B    업체 C
       한국어가 자연스러움
       내용이 정확함 (틀린 정보 없음)
       자취생에게 실용적
       사진을 잘 읽음 (사진 4문항만)
       형식을 지킴 (카드/JSON/길이)
       응답 속도 (초)
       한 번 호출 비용 (대략)
     여러 사람이 각자 점수를 주고 평균을 낸다 (한 사람 취향으로 정하지 않기).
  5) 위험한 답 확인: 틀린 법률/안전 조언이 있는지 본다.
       예) 계약·보증금 답변이 단정적으로 틀리면 곤란하다.
       "법률 조언이 아니에요" 같은 안내를 붙이는 게 좋다.
  6) 한도/오류 확인: 짧은 시간에 요청을 여러 번 보내서 제한에 걸리는지, 오류 메시지가 어떤지 본다.
  7) 결정: 점수 + 비용 + 무료 한도 + 개인정보 조건을 함께 보고 "기본 업체 1곳 + 대체 1곳"을 정한다.

[D] 개인정보 / 약관에서 챙길 것
  - AI 에 보내는 질문과 지출 요약에는 사용자 정보(월세, 지출 등)가 섞일 수 있다.
  - 이름, 전화번호, 정확한 주소 같은 식별 정보는 AI 에 보내지 않도록 서버에서 걸러낸다.
  - 개인정보 처리방침에 "AI 제공 업체에 질문 내용이 전달된다"는 내용을 넣는다.
    해외 업체면 국외 이전 고지도 필요하다. 지금 약관은 초안이라 법률 검토 때 함께 본다.
  - 사진은 용량을 줄여서 보낸다 (프론트가 이미 프로필 사진은 줄여서 보내는 방식이 있음).
  - 사용자가 대화를 지우면 서버 기록도 지워지는지(DELETE /api/ai/conversations/{id}) 확인한다.

[E] 처음에 추천하는 진행
  1) 지금은 정해진 답변(가짜)이므로, 먼저 인터페이스(B)와 대화 저장 API 부터 만든다.
  2) 업체 1곳으로 연결해서 화면에서 동작하는지 확인한다.
  3) 그 뒤 2~3곳을 C 방법으로 비교해서 기본 업체를 바꾸거나 확정한다.
  4) 무료 한도가 적은 업체를 쓸 때는 하루 사용량 제한(ai_usage_daily)을 더 낮게 잡는다.

8. 굳이 안 써도 되는 것 (지금 단계에서는 과함)
====================================================================
  - 마이크로서비스(MSA): 서비스 규모에 비해 너무 복잡하다. 하나의 Spring 앱(모놀리식)으로 충분
  - GraphQL: 프론트가 이미 REST 방식(/api/...)으로 약속되어 있다
  - Thymeleaf 등 서버 화면 렌더링: 화면은 React 가 담당한다
  - MongoDB 등 다른 DB: 이미 MySQL 스키마가 있다
  - Kafka 등 메시지 큐: 알림/AI 요청량이 크지 않은 동안은 불필요
  - 쿠버네티스: 배포가 필요한 시점에 Docker 만으로 시작해도 충분


9. 개발 환경 / 배포 (무료 위주)
====================================================================
  개발
    - IDE: IntelliJ IDEA (Community 로도 가능, Ultimate 는 학생 무료 제공이 있는 경우가 많음)
    - MySQL: Docker Compose 로 실행 (팀원 모두 같은 환경)
    - API 테스트: Swagger UI 또는 Postman / IntelliJ HTTP Client
    - .env: 서버 비밀 키는 .env 에만 (깃에 올리지 않음. README.md 의 .gitignore 안내 참고)
  배포 (필요해질 때)
    - 프론트: 정적 파일이라 Vercel / Cloudflare Pages 등 무료 티어로 가능
    - 백엔드 + MySQL: 무료 한도가 있는 호스팅이 자주 바뀐다. 발표/시연용이면
      내 컴퓨터에서 Docker Compose 로 실행하는 것이 가장 확실하다.
    - 도메인/HTTPS 가 필요하면 그때 호스팅을 정한다 (소셜 로그인 redirect 주소도 그때 등록)


10. 이 스택으로 처음 만드는 순서 (필수기능 목록 15번과 연결)
====================================================================
  1) start.spring.io 로 프로젝트 생성 (위 3번), Docker Compose 로 MySQL 실행, schema.sql 적용
  2) common: 오류 응답, Long->String 직렬화, 시간대, CORS, JWT/Security 설정
  3) auth: signup / login / me / logout  -> 프론트 .env 의 VITE_USE_MOCK=false 로 실제 연결 테스트
  4) user(설정, 동네), event, money  (홈과 마이페이지 핵심)
  5) notification, memo, support
  6) community + 파일 업로드 + 신고
  7) admin / 이용 정지, 약관
  8) 휴대폰 인증, 소셜 로그인 (외부 서비스 연결)
  9) AI, 지도 장소, 날씨/주소 서버화
  각 단계가 끝나면 Swagger 로 확인하고, 프론트 해당 기능을 localStorage 에서 API 호출로 바꾼다.
