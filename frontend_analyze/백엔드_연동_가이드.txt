ZIP 백엔드 연동 가이드 (프론트 코드를 읽지 않고도 백엔드를 만들 수 있게)
====================================================================
작성일: 2026-11-01
대상: frontend/src  (코드를 직접 확인하고 정리함)
함께 볼 문서:
  - frontend/API.md        API 주소와 요청/응답 모양을 정한 "계약서" (이 문서보다 자세함)
  - backend/openapi.yaml  API.md 와 같은 내용을 Swagger(OpenAPI 3.0.3)로 쓴 파일 (주소 81 · API 115)
  - db/schema.sql          DB 표 정의
  - frontend_구조_설명.txt  폴더 구조 설명

이 문서의 역할
--------------------------------------------------------------------
API.md 가 "어떤 주소로 무엇을 주고받나"라면,
이 문서는 "그 데이터를 화면이 어디서 어떻게 쓰고 있나, 서버가 뭘 대신 해줘야 하나"를
화면별로 풀어 쓴 지도다.
읽는 순서: 1번(한눈에 표) -> 2번(id/이름 규칙) -> 3번(기능별 상세) -> 4~6번(주의점)


0. 지금 상태 한 줄
====================================================================

-> 백엔드가 생기면 각 기능의 store.ts 가 하던 일을 API 호출로 바꾸면 된다.

2. "id"와 "이름"으로 연결되는 방식 (백엔드가 가장 헷갈릴 부분)
====================================================================
프론트는 DB id 를 쓰지 않고 이름(문자열)이나 임시 숫자로 연결하는 곳이 많다.
서버를 붙일 때는 아래처럼 바꿔야 한다.

[2-1] id 의 모양
  - 프론트 코드의 id: 대부분 숫자 (Date.now() + 난수로 만든 임시 값)
      예) Bill.id, CalEvent.id, MoneyRecord.id, Memo.id, Post.id
  - API 약속: DB 의 BIGINT id 를 "문자열"로 준다 ("id": "12")
  - 일부는 이미 문자열이다: User.id, Inquiry.id, CustomPreset.id, 알림 id
  -> 서버가 문자열 id 를 주면 프론트가 타입을 string 으로 맞춰서 붙인다.
     (서버는 항상 문자열로만 주면 된다)

[2-2] 이름(문자열)으로 연결되는 것  -> 서버에서는 id(FK)로 바뀜
  일정 카테고리   CalEvent.category = '집 관리' 같은 "이름"
                  서버: events.category_id -> event_categories.id  (NULL = 미분류)
                  이름을 바꾸면 그 카테고리의 일정/항목 이름도 같이 바뀐다 (프론트 renameCategory)
                  카테고리를 지우면 일정/항목은 "미분류"로 간다 (deleteCategory)
  우리 동네       settings.region = '서울 마포구' 같은 "이름"
                  Post.region 도 이름
                  서버: users.region_id -> regions.id.  주소에서 구를 찾아 연결, 못 찾으면 null
  지도 장소 id    "종류:이름" 형태의 문자열 (예: '약국:○○약국') — zip-map 의 favs 에 저장
                  서버: places.id, 즐겨찾기는 place_favorites
  글 작성자       Post.author = 닉네임(문자열), Post.mine = 내 글인지(true/false)
                  서버: 글 응답에 author(닉네임)와 mine 을 계산해서 같이 줘야 함
  일정 반복 id    기념일이 매년 반복될 때 화면용 id 를 "12@2027" 처럼 만든다.
                  서버로 보내는 id 는 앞부분 원본 id("12")만 쓴다. 서버는 한 번만 저장하고
                  yearly=true 로 표시만 하면 된다 (달력에 그 해마다 보이는 건 프론트가 계산).

[2-3] 값 규칙
  금액      원 단위 정수. 예외: settings.rent(월세)만 "만원 단위". (API.md 0번)
            온보딩 설문(zip-housing-survey)은 모두 원 단위. 설문 월세가 설정으로 들어갈 때
            원 -> 만원 변환이 필요하다. (프론트가 처리하지만 서버에 저장할 때 단위를 정해야 함)
  날짜      'YYYY-MM-DD', 시각 'HH:MM'(빈 문자열 = 종일), 월 'YYYY-MM'
  시각      Post.ts 는 밀리초(ms). API 약속은 ISO 문자열 -> 서버는 ISO 로 주면 프론트가 변환
  카테고리  커뮤니티 글 분류는 화면에서 한글('자유','꿀팁','질문','동네'),
            API/DB 는 영문 코드(TIP, GENERAL 등). 매핑표가 필요하다 (API.md 7번, schema.sql 확인)
  provider  로그인 방법은 소문자('email','kakao','google','naver')로 내려준다


3. 기능별 상세
====================================================================

[3-1] 로그인 / 회원 (features/auth)  --  API.md 1번, 이미 연결 코드 있음
--------------------------------------------------------------------
프론트 파일
  api/realAuthApi.ts   실제 서버 호출 (아래 주소로 이미 요청함)
  api/mockAuthApi.ts   가짜 서버 (서버 없을 때만 사용)
  store/authStore.ts   로그인 토큰과 내 정보 보관 (localStorage 'zip-auth')
  types.ts             요청/응답 모양 (백엔드와 이야기할 때 기준이 되는 파일)
  schema.ts            입력 검사 규칙 (서버에서도 똑같이 검사해야 함)

이미 프론트가 호출하는 주소 (백엔드만 만들면 바로 연결됨)
  POST   /api/auth/signup                    회원가입
  POST   /api/auth/login                     로그인 (아이디 또는 이메일)
  POST   /api/auth/logout
  POST   /api/auth/refresh                   (선택) 토큰 재발급, 재발급 토큰은 httpOnly 쿠키
  GET    /api/auth/me                        토큰으로 내 정보
  PATCH  /api/auth/me                        닉네임 수정 또는 소셜 첫 가입 정보
  PATCH  /api/auth/me/password               비밀번호 변경
  DELETE /api/auth/me                        탈퇴
  POST   /api/auth/phone/send, /phone/verify 휴대폰 인증번호 보내기/확인
  POST   /api/auth/find-id                   아이디 찾기
  POST   /api/auth/password-reset/verify, /password-reset
  GET    /api/oauth2/authorization/{kakao|google|naver}  (끝나면 /oauth/callback?token=... 으로)

공통 약속
  - 모든 요청에 Authorization: Bearer <accessToken> 이 자동으로 붙는다 (lib/apiClient.ts)
  - 401 이 오면 프론트가 자동 로그아웃한다 (app/setupApi.ts)
  - 실패 응답은 { "message": "..." } 이고 그 문장이 화면에 그대로 보인다
  - API 주소 앞부분은 VITE_API_BASE_URL (기본 '/api')
  - 로그인 정보 저장 위치: '로그인 유지'를 켜면 localStorage, 끄면 sessionStorage (키 'zip-auth').
    그래서 서버의 세션 만료도 remember 값에 따라 길게/짧게 달라져야 자연스럽다.

서버가 판단해서 내려줘야 하는 user 필드
  firstLogin     처음 로그인이면 true -> 프론트가 /onboarding 으로 보냄
                 (서버는 로그인 처리 직전 users.last_login_at 이 NULL 이었는지로 판단)
  agreedAt       null 이면 소셜 첫 가입 -> /welcome (약관 동의 + 주소 입력) 으로 보냄
  role           'ADMIN' 이면 /admin 화면만 보임
  status/suspension/warnCount/unseenWarnings  이용 정지/경고 (3-12 참고)

[3-2] 첫 로그인 설문 (features/onboarding)  --  housing_surveys 및 API.md 2번 제안 참조
--------------------------------------------------------------------
흐름: 로그인 응답 firstLogin=true -> /onboarding -> 설문 -> "ZIP 시작하기" -> firstLogin 해제
질문(HousingSurvey 필드)
  birth(생년월일) / address(간략한 주소) + addressPoint(좌표, 선택)
  kind: 'monthly'(월세) | 'jeonse'(전세)
  deposit(보증금) rent(월세) mgmtIncluded(관리비 포함 여부) mgmtFee(관리비)
  contractFee(계약금) hasLoan loanAmount (+ loanAnnualRate, loanPaymentDay, loanStartDate)
  income(수입) incomePeriod: 'monthly' | 'annual'
  answeredAt, userId
설문이 끝나면 프론트가 다른 곳에도 값을 채운다
  - 월세 -> 생활 설정(settings.rent, 만원 단위)
  - 관리비 -> 고정지출 항목(태그 '관리비')
  - 주소 -> settings.region / 좌표
백엔드가 정해야 할 것
  1) housing_surveys 최신 응답 한 행과 user_settings 월세/지역 동기화
  2) API.md의 GET/PUT /api/me/housing-survey 제안 구현
  3) firstLogin은 첫 로그인 여부, 설문 완료는 설문 GET 결과로 별도 판정
  (테스트용 가짜 계정 a1 / b1 은 mock 전용. 서버에는 필요 없음)

[3-4] 일정 (features/life, CalEvent)  --  API.md 3번
--------------------------------------------------------------------
CalEvent: id, date, time, title, done(완료 체크), category(이름), anniv(기념일), yearly(매년 반복)
  - "할 일"은 따로 없고 일정에 done 체크로 합쳐졌다 (DB events.is_done, done_at)
  - anniv=true 인 기념일은 완료 체크/남은 일 개수에 들어가지 않는다
  - 쓰레기 배출 일정은 저장하지 않는다: 프론트가 요일표(data/catalog.ts 의 TRASH 상수)로
    매번 계산해서 달력에 읽기 전용(TrashEvent)으로 얹는다.
    -> 서버는 GET /api/trash-schedules?regionId= 로 "요일별 배출 정보"를 주면 된다.
API: GET/POST /api/events, PATCH/DELETE /api/events/{id}, PATCH /api/events/{id}/done,
     GET /api/events/search?q=, GET/POST/PATCH/DELETE /api/event-categories,
     GET/POST/PATCH/DELETE /api/event-presets
카테고리 기본 5개 + 사용자가 만든 것 + '미분류'. 이름 변경/삭제 시 일정도 같이 옮겨야 함(2-2).
[주의] 기념일 칸 이름
       DB(schema.sql, 정식 마이그레이션 20261031_02_event_anniversaries.sql)는 is_anniversary / repeat_yearly 다.
       API 의 JSON 키는 anniv / yearly 그대로 쓴다 (DB 칸 설명에 "API anniv/yearly"로 적혀 있음).
       API.md 17번 행, db/README.md, db/migrations/README.md 도 이 이름으로 맞춰 두었다.
       db/migrations/20261101_event_anniversary.sql 은 DEPRECATED(실행 금지)로 표시되어 있다.
       백엔드는 DB 기준 이름(is_anniversary/repeat_yearly)을 쓰면 된다.

[3-5] 월세 / 고정지출 (features/life FixedExpense)  --  API.md 4번
--------------------------------------------------------------------
월세 납부 체크: rentPaid = { 'YYYY-MM': true/false }  -> 서버 rent_payments (달마다 한 줄)
공과금(Bill): id, name, amount(원), tag, paidMonth
  - tag 는 '공과금','통신','구독','관리비','기타' 중 하나
  - paidMonth = 마지막으로 납부 체크한 달('YYYY-MM'). 이번 달과 같으면 납부 완료,
    달이 바뀌면 저절로 미납으로 돌아간다 (그래서 "새 달 시작" 버튼이 없음)
    -> 서버는 bill_payments(bill_id, month) 로 달마다 기록하고, 조회 시 ?month= 로 그 달 납부 상태를 계산해 준다
API: GET /api/rent-payments?from=&to=, PUT /api/rent-payments/{month},
     GET /api/bills?month=, POST /api/bills, PUT /api/bills/{id}/payments/{month}, DELETE /api/bills/{id}
삭제는 해지 처리(is_active = 0)

[3-6] 가계부 (features/life MoneyLog, 수입/지출)  --  API.md 5번
--------------------------------------------------------------------
MoneyRecord: id, date, cat(분류 이름), amount(원), memo, incomeType('fixed' | 'other', 수입만)
  - 수입과 기타 지출은 모양이 같다
  - cat 은 이름이지만 서버에서는 ledger_categories.id (categoryId)
통계는 프론트가 계산하는 중 (derive.ts 의 spendBreakdown 등)
  -> 서버에서는 GET /api/stats/monthly-income, /api/stats/spend-breakdown 으로 줄 수 있음
  (프론트 계산 결과 = 월세(월세 계약일 때만) + 고정지출 합 + 대출 이자 + 기타 지출 을 분류별로 합친 값.
   고정지출 합은 "공과금"으로, 대출 이자는 "대출 이자"로 묶여 나온다)
API: GET/POST/DELETE /api/incomes, /api/expenses, GET /api/ledger/categories?kind=

[3-7] 알림 (features/life NotiCenter, derive.ts 의 buildNotis)  --  API.md 6번
--------------------------------------------------------------------
지금은 서버 알림이 아니다. 프론트가 일정과 설정을 읽어서 "알림을 계산해서 만든다".
실제로 계산하는 알림 (buildNotis)
  - 오늘~3일 안의 일정과 기념일 (끝낸 일정은 제외)
  - 오늘~3일 안의 쓰레기 배출 (요일표 기준)
